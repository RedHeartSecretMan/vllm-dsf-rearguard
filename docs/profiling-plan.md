# 当前硬件性能摸底计划

目标平台为 `8×A100-SXM4-80GB / NVSwitch`。全部推理测试、PPL、GPQA 和压力测试使用 `127.0.0.1:6688`。先完成 1M / 0.90 的完整基准，再单独核对 chunk 候选，随后完成上下文与显存水位矩阵；最终在选出的配置上运行一次 GPQA 和一次 30 分钟压力测试。

当前执行策略为 **v2（`policy_version=2`，`single_formal_v2`）**：每个适用单元正式执行一次，逐点预热缩短为一轮 C2、输出最多 2 token。已经保存的 v1 三轮结果保留；其中 `repeat-1` 作为 v2 对照主值，`repeat-2/3` 作为补充记录，不并入主值，也不挑选最快的一轮。复用记录须绑定原始 attempt、请求摘要和运行身份，并保留原预热策略；仅作为执行策略变化处理，不改写旧回执。

## 输入与固定参数

所有组复用同一镜像 ID、1017 权重、适配源码指纹和冻结输入。固定 TP4 / DP2 / EP8、全局 `max-seqs=256`、DSpark k5、OMP 8、EPLB、custom AG/RS、stacked-kv、bounded-prefill、FP8 KV；关闭 prefill throttle、decode-metadata、ragged-reuse，`logits-row-chunk=0`。多模态分块开启，每请求 64 张图片、2 个视频，每视频最多 32 帧、目标 1 FPS。Responses store 开启且只有一个 API server。

本轮 11 个负载单元的结果支持保留 16K 和 32K 两个 chunk 候选，不能替代完整 ISL / OSL 矩阵。主矩阵先固定 16K；32K 对照单独改变 chunk，使用相同 42 点、相同 payload 与重复次数。32K 关闭多模态分块的结果保留为已完成的兼容与性能参照。

| 轴 | 取值 |
|---|---|
| 最大上下文 | 1048576、524288、262144 |
| 显存水位 | 0.90、0.93、0.96 |
| 主矩阵组数 | 9，1M / 0.90 基准计入其中 |

## 受控测量

所有矩阵点、短性能、单请求 prefill / decode、工具历史及图文混合各正式测量一次。超长 C4 / C16 容量、300 秒混合、核心功能、视觉、Responses 和 PPL 仍每组各一次；GPQA 和 soak 仍为全计划各一次。这些次数对所有组相同，预热与正式结果分开。v2 报告单次观测值；请求级延迟分位数仍按该轮全部请求计算，不把单次观测表述为重复测量中位数或稳定性能结论。

每次服务启动后保留两轮 C256 通用预热，每请求输出 128 token，以覆盖 decode 路径并验证两个 DP 实例。每个性能单元先执行一轮 C2 预热，输入长度保持原形状，输出预算为 `min(正式 OSL, 2)`；单请求 prefill 的正式 OSL 为 1，因此预热也输出 1 token。通过实际 `engine=0/1` 的输入和生成 token 计数增长确认双 DP 覆盖，图文预热仍使用最大 4 图输入。

只有等待异步 metrics 后仍未证明双 DP 都处理了该输入形状，或收到明确的 HTTP 503 / not-ready 响应时，才最多追加两轮预热，并在请求前记录触发原因和新增请求。已完成且证据有效的预热不机械重复；追加前的原始响应与失败记录全部保留。其他 HTTP 错误、OOM、真实编译错误、缓存/长度校验失败或缺少可验证的 metrics 均停止该次预热并交由诊断，不通过自动重试覆盖失败。

每个性能单元、轮次和请求使用独立的合法缓存盐，组间重放同一 payload。随机输入由 catalog seed、单元、轮次和请求序号确定；v2 固定使用 `repeat-1`，与被复用的 v1 第一轮一致。该构造与历史输入不能仅凭 seed 名义相同就直接比较。冷 KV 必须逐请求观测到 `cached_tokens=0`。视觉编码缓存与 KV 分开描述：复用已校验的媒体并预热，保留采样计数，不把冷 KV 当作冷编码器。视频历史及 Responses 协议续轮保留其正常历史/缓存行为，单独标明。

原 300 秒 mixed 是闭环负载，请求数随处理速度变化。本次另用明确标记的 `fixed_arrival_schedule` 执行变体：5 批各 64 个 decode 请求，分别在 0 / 60 / 120 / 180 / 240 秒提交；15 个 prefill 请求每 20 秒提交一次。保留 C64 / C2 在途上限、原输入输出长度和 300 秒到达窗口。所有组共 335 个相同请求；记录提交等待、从计划到达到首 token/完成的延迟及排空时间。结果不与历史闭环 TPS 直接计算提升比例。

PPL 使用冻结的 272936 token、134 个非重叠 2048-token 窗口，`echo`、`top_k=1`、seed 1017；输入文本哈希与历史一致。每窗保存原始请求/响应和 logprobs，缺失/非零缓存或错误长度单独记为失败。GPQA 使用服务器安装的 bidevs，198 题、单轮、batch 32、temperature 0、top_p 0.95、输出预算 65536、reasoning effort max；工具版本与历史版本差异会记录。

2026-10-25 11:40（北京时间，03:40 UTC），1M / 0.95 / 16K 组在 `matrix_concurrent/nature/i256-o1000-c256` 的三轮结果全部落盘、两个 DP 的在途请求均为 0 后，切换到 v2 runner，沿用原模型服务。交接时已有 37 个 `PASS` 单元，当前单元的逻辑状态仍为 `IN_PROGRESS`，但三轮结果已经完整保存；核验原始回执后，共 38 个单元复用 `repeat-1`，剩余 47 个适用单元按 v2 执行。旧轮次和状态不改写，也未重新加载模型。此前 16K / 0.96 的启动预热失败、32K / 0.90 的 1M 预热失败仍保留为原始 `FAIL`，本次策略切换不将其改为通过或未执行。

最终一次性项目由 [`gpqa_bidevs.py`](../scripts/acceptance/gpqa_bidevs.py) 和 [`profile_soak.py`](../scripts/benchmarks/profile_soak.py) 执行。GPQA wrapper 检查单轮 198 题，并核对 bidevs 原生预测、评分和日志；逻辑题目数量与 HTTP 尝试/重试数量分别记录。离线汇总入口 [`profile_report.py`](../scripts/benchmarks/profile_report.py) 核对最终九组、全部适用 case、可比条件、失败处理和一次性项目；缺少任一必跑回执不能输出 `FINAL_PASS`。

每组记录实际 KV 容量，输入/输出/总 token 吞吐、TTFT / TPOT / 端到端延迟及分位数、输入输出长度、成功率、缓存命中、等待队列、抢占/重计算和 OOM/服务异常。不存在的运行时指标标为未提供，不推断为零。相同 case、相同输入和测量条件才计算变化，不把不同工作负载的 TPS 平均成综合分数。

失败和重试使用独立 attempt 目录；阶段完成只表示该阶段，不代表九组及 GPQA/soak 全部完成。最终报告必须核对全部预期组合和一次性项目的真实回执，再给出分场景推荐配置。
