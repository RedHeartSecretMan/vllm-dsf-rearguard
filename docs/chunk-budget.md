# 16K / 32K 基础性能对照

当前 1M 视觉服务采用 `--chunk 16384 --no-disable-chunked-mm-input`：相对同样开启多模态分块的 32K，运行时报告的可用 KV 显存从 5.43 GiB 增至 10.50 GiB，视频 C4 输出 token 吞吐提高 4.55%。代价是 64K / 260K 冷 prefill 输入 token 吞吐分别降低 4.87% / 3.40%，短文本 C128 / C256 吞吐降低 7.21% / 4.42%。纯文本吞吐和长 prompt 首包优先时，可选择 32K。

这次仅为当前服务选择显式启动参数，`launch.py` 的 chunk 默认值仍为 32768。测试端口为 `6688`，正式服务默认端口为 `6789`。

## 测试配置

测试于北京时间 2026-10-24 23:57 至 2026-10-25 00:36 在 `8×A100-SXM4-80GB / NVSwitch` 上执行。固定 1017 权重、1M 上下文、TP4 / DP2 / EP8、DSpark k5、OMP 8、EPLB、custom AG/RS、stacked-kv、bounded-prefill、`gpu-memory-utilization=0.90`、全局 `max-seqs=256`，关闭 prefill throttle。Responses store 开启，API server 数量为 1。每请求上限为 64 张图片、2 个视频；视频最多采样 32 帧，目标 1 FPS。

| 配置 | chunk 预算 | 多模态分块参数 |
|---|---:|---|
| 32K / 关闭分块 | 32768 | `--disable-chunked-mm-input` |
| 32K / 开启分块 | 32768 | `--no-disable-chunked-mm-input` |
| 16K / 开启分块 | 16384 | `--no-disable-chunked-mm-input` |

三组均支持图片和视频；“分块”指多模态输入能否跨 prefill 调度窗口。32K 两组隔离开关的影响，开启分块的两组隔离 chunk 预算的影响。

三组使用同一镜像 `sha256:235c0fa37f92eb29a7ec0a959e82da9e3c5cf559dec54099939a4971db9a1653`，适配源码指纹为 `98d985dde17f699d411ae376ac55481c4660140c5074360a15308c68535fa006`。runner 来自 `64b48b3`，冻结 workload 的内容摘要为 `ea6cbfec447f454bb4dc71c46bd447904a0a7b3217bca49f00d67c9083086cc0`。

每组 11 个负载单元，每个执行 3 轮，共 99 轮、4,293 个计量请求，全部成功；另有 33 个单请求预热。三组接收相同 payload，每个请求和重复轮使用独立 `cache_salt`，逐请求验证 `cached_tokens=0` 及固定输出长度。文本使用固定 seed 的随机 token；图像与视频复用合成媒体，测量前预热，编码器缓存未单独清空。

视频源长 96 秒、1200×1200，实际采样 32 帧，每帧视觉 span 为 872 token，合计 **27,904 个视觉 token**，加上 prompt 和 wrapper 后输入为 28,323 token。该视频在 16K 配置下必须跨窗口处理。矩阵结束后，另用同一视频执行语义检查：输入 28,320 token，输出正确的数字顺序 `[1, 2, 3]` 和颜色顺序 `["red", "green", "blue"]`。

## 统计说明

吞吐按每轮整批请求的输入、输出或总 token 数除以该轮墙钟时间计算，定义见 [指标口径](benchmarks.md#指标口径)。下表为 3 轮中位数，括号为最小值至最大值；延迟列为各轮分位数的中位数。`C` 表示并发数，文本 case 名中的两个数依次为 ISL / OSL，图片与视频 case 的 OSL 均为 128。

16K 首个单流 case 的第一轮 TTFT 为 1.379 秒，后两轮为 0.182 / 0.162 秒。原始三轮吞吐仍全部保留。全矩阵结束后，用相同三份 prompt、仅替换 cache salt 的独立补测得到 208.79 / 213.50 / 221.80 token/s，TTFT 为 0.181 / 0.180 / 0.186 秒，支持首轮存在暂态影响。补测未替换主表，也未并入其中位数。

三组按固定顺序运行，每个负载只有 3 轮。短请求部分区间重叠较多；本轮未覆盖持续混合到达或长时间生产负载。视频 C4 中，16K 组的三轮吞吐区间与两组 32K 的区间均未重叠，但不能由此推断所有视频负载均有同等收益。KV 容量增大也不等同于已实测 1M 并发能力同比增加。

完整统计、启动日志容量记录、补测和原始文件摘要见 [结果 JSON](evidence/chunk-budget-20261025.json)。

## 复现

使用 Python 3.10 或更新版本，准备媒体需要 `ffmpeg`。先查看三组完整启动参数，并在服务器的 `6688` 端口启动第一组服务：

```bash
python3 -m scripts.benchmarks.chunk_budget --plan
```

服务启动后只生成一次 workload，随后三组均复用同一个文件：

```bash
python3 -m scripts.benchmarks.chunk_budget --prepare-workload \
  --base-url http://127.0.0.1:6688 --run-id chunk-budget-comparison \
  --fixtures-dir runtime/chunk-budget/fixtures \
  --workload runtime/chunk-budget/workload.json
```

每组均通过 `launch.py --start` 启动独立容器，使用相同镜像、权重和公共参数。将对应的启动回执传给 runner；输出目录必须是新目录：

```bash
python3 -m scripts.benchmarks.chunk_budget --profile 32k_mm_off \
  --base-url http://127.0.0.1:6688 \
  --launch-receipt runtime/LAUNCH_TIMESTAMP/launch.json \
  --workload runtime/chunk-budget/workload.json \
  --output runtime/chunk-budget/32k_mm_off
```

完成后停止该组，依次启动 `32k_mm_on`、`16k_mm_on`，替换 profile、启动回执和输出目录。runner 校验端口、镜像中的适配源码、服务容器身份、部署参数、payload 摘要和每个请求的缓存状态。三组比较时还应核对使用相同镜像 ID 与 workload 摘要。

本轮原始结果保存在服务器 `/tmp/dsv41-chunk-ab-20261024/` 和本地 `runtime/chunk-ab-20261024/`。端口调整前在 `8005` 上中止的尝试单独保存在 `attempt-8005-excluded/`，未计入本报告。

## 最终服务

测试结束后，容器 `dsf-main-64b48b3` 使用 16K 分块配置启动于 `http://127.0.0.1:6789`，`/health` 和 `/v1/models` 均检查通过。`6688` 的测试容器已停止。新镜像为 `sha256:c1a37e834eecdb77a89c5b6b182d96b6ef3492f2b417af94abd7752fc1b3c520`，与三组测试镜像的 43 个适配源码文件指纹一致；本轮修改限于启动端口、benchmark runner、配置和文档。

本机使用 uv 管理的 Python 3.10，164 项测试完成、8 项因环境条件跳过；镜像构建中 178 项测试完成、5 项跳过。Ruff、配置与文档引用检查通过。正式端口只执行健康检查和模型列表查询，性能数据均来自测试端口。
