# 性能与调优

本文给出 DeepSeek-V4.1-Flash-1017 在 `8×A100-SXM4-80GB / NVSwitch` 上的配置建议、测试方法和性能数据。核心数据来自 262K、524K、1M 三档上下文与 0.90、0.925、0.95 三档显存水位组成的 9 组配置矩阵：性能项覆盖短请求并发、单请求 prefill / decode、ISL / OSL 矩阵、1M 长请求容量、工具历史、图文混合和固定到达混合负载，每组还运行功能、协议和全模型 PPL 测试，723 个适用测试项全部通过。此外，本页还记录了 1M 配置下的闭环混合负载与 30 分钟持续负载、16K / 32K 分块预算和多模态分块对照，以及未进入默认配置的候选方案。功能、协议和 GPQA Diamond 的结果见[验证结果](validation.md)。

## 配置建议

| 场景 | 建议 |
|---|---|
| 首次部署 | 1M 上下文、16K chunk、0.90 显存水位，开启多模态分块、`stacked-kv` 和 `bounded-prefill` |
| 输入长度可控 | 选择能容纳最长输入与最大输出的上下文，再在目标负载上比较水位 |
| 需要更大 KV 容量 | 评估 0.925 或 0.95，并结合启动日志、allocator 告警和延迟确认效果 |
| 视觉或长输入负载 | 优先使用 16K chunk；1M 上下文使用 32K chunk 时需要 0.95 水位 |
| 解码延迟优先的混合负载 | 可评估 `prefill-throttle`；它会提高 decode 流吞吐，但会降低 prefill 流吞吐 |

水位不是越高越好。更高水位会增加 KV 容量，但不同负载的吞吐和尾延迟变化并不一致。部署时应以启动日志中的实际 KV 容量和目标负载实测为准。

## 测试方法

性能表区分整机吞吐和单请求指标。输入、输出和总 token TPS 使用同一轮测试的墙钟时间；单请求 Prefill TPS 为输入 token ÷ TTFT，Decode TPS 为输出阶段速率。配置矩阵每项报告第一次正式测量的结果；基础分块对照报告三轮中位数，并列出最小值和最大值。表中 `NA` 表示输入加输出超过上下文容量，`/` 表示未进入正式测量，`—` 表示该指标不适用。

### 输入与准入

所有配置使用同一组固定输入。random 使用随机 token ID，nature 使用固定语料经目标 tokenizer 得到的 token 序列；两者保持声明 ISL。独立 prefill 使用重复词，单独比较。同一输入重复测量时只更换 `cache_salt`，输入内容和测试参数保持不变。

矩阵使用 `temperature=0`、OSL=1000 和 `ignore_eos=true`。输入加输出超过上下文容量的项目记为不适用，测试不截短输入。大海捞针测试使用固定消息，按目标长度的容差准入。

262K、524K、1M 分别有 76、80、85 个适用测试项，包含性能、功能、协议和 PPL；每组 PPL 的 134 个窗口计为一个测试项。

### 预热与缓存

服务启动后先执行两轮 C256 通用预热，每个请求输入 1024 token、输出 128 token，并确认两个 DP 实例都参与计算。

每个性能项在正式测量前还会按表中“逐点预热”列执行预热：

- `1×C2×≤2`：逐点预热 1 轮，并发 2 个请求，最多生成 2 个 token。
- `2×C2×128`：逐点预热 2 轮，并发 2 个请求，每个请求生成 128 个 token。
- `通用启动预热`：使用服务启动阶段的统一预热，表中没有单独的逐点预热。

失败、长度异常和缓存异常单独记录，不计入正式性能结果。

预热和正式请求使用不同的 `cache_salt`，正式请求要求 `cached_tokens=0`。视频历史和 Responses 续轮保留协议本身的缓存行为。

### 指标口径

C 表示并发请求数，ISL / OSL 分别为输入和输出 token 数。

| 指标 | 定义 |
|---|---|
| 输入 / 输出 / 总 token TPS | 成功请求对应 token 总数 ÷ 整轮墙钟；三者分母相同 |
| TTFT | 请求发出至首个携带输出的 SSE 事件 |
| 单请求 Prefill TPS | 输入 token ÷ TTFT |
| 单请求 Decode TPS | (输出 token 数 − 1) ÷ 首个与最后一个有效输出事件的间隔 |
| TPOT | 同一间隔 ÷ (输出 token 数 − 1) |
| ITL | 相邻 SSE 事件间隔；DSpark 可在一次事件中返回多个 token |
| E2E | 单个请求发出至完成的时间 |

请求分位数采用 nearest-rank；C1 行是单请求观测。不同输入长度、并发或数据集的 TPS 不求综合平均。

### 混合负载

固定到达混合负载在 0/60/120/180/240 秒各提交 64 个 decode 请求，另每 20 秒提交一个 prefill 请求，共 320 + 15 = 335 个请求，各配置使用同一组请求。Decode 为 ISL 1024 / OSL 1000、最多 64 个并发；prefill 为 ISL 262144 / OSL 1000、最多 2 个并发。到达窗口为 300 秒，结果包含排空时间。

两流和整场吞吐都除以同一整场墙钟。HTTP TTFT 从实际提交开始计时；计划到达至完成还包含客户端限流等待。闭环混合负载按完成速度生成请求，不能与固定到达负载直接比较。

### 精度与稳定性测试

PPL 使用 wikitext-2 test，共 272,936 个 token、134 个非重叠窗口。每窗最多 2,048 token，首 token 不计分，共 272,802 个计分 token；请求使用 `echo`、`top_k=1` 和 `seed=1017`。

GPQA Diamond 使用 198 题、batch 32、`temperature=0`、`top_p=0.95`、输出预算 65,536 token 和 `reasoning_effort=max`；持续负载测试时长为 1,800 秒。结果见[验证结果](validation.md)。

### 结果解读

KV 列为测试时启动日志报告的容量，实际部署应以当前启动日志为准。allocator 列统计日志告警行数，不等于失败请求数。配置矩阵每项只有一次正式测量，预热方式也不完全相同，相近的数值差异不作为稳定排名依据。

## 基础负载

| 场景 | 观测与选择依据 |
|---|---|
| 262K 短 C256、260K prefill、独立 decode | 这三个负载的三水位差异均小于 1%，优先按容量和余量选择 |
| 524K 短 C256 | 0.90 输出 7045 token/s，0.925/0.95 为 6441/6548 token/s |
| 1M 短 C256 | 0.925 输出 6908 token/s，0.90/0.95 为 5573/6758 token/s；预热规格有差异 |
| 1M 长请求容量 | C4、C16 均成功；更多 KV 容量未带来一致的吞吐提升 |
| 数据分布 | 262K、ISL16384/C256 的 0.95 相对 0.90，random 为 −7.70%，nature 为 +3.45% |

配置矩阵统一使用 16K chunk。比较不同水位时，应使用同一上下文、同一输入长度和同一并发。PPL 结果见[验证结果](validation.md#全模型-ppl)。

### 分块预算

16K 与 32K 的选择需要同时考虑吞吐、KV 容量和长输入边界。1M / 0.90 的 42 个对应负载中，32K 完成 40 项正式测量，输出吞吐有 15 项高于 16K、25 项低于 16K，变化范围为 −32.68% 至 +43.87%，没有一致的方向；random 和 nature 的 1,047,000 token 输入未完成预热。完整资源预算下，32K 需要为初始化和图捕获预留更多显存；1M / 32K / 0.95 的长输入验证见[资源边界](validation.md#长输入与资源边界)。

### 工作区、通信与调度

配置矩阵固定开启 `bounded-prefill`、OMP 8、EPLB 和 custom AG/RS；`prefill-throttle` 按负载显式启用。以下对照提供这些选择的依据。

<details>
<summary>查看 bounded-prefill 工作区对照</summary>

1M 配置。对照参数是 `bounded-prefill`：关闭时按多请求上界预留 indexer prefill 工作区，开启时把预留收敛到单个完整上下文请求所需的压缩行数，较大的多请求 prefill 由 metadata builder 拆成多个 chunk。两组使用相同的镜像、基础配置、1K 输入和 128 输出，C256 使用相同的 seed 8080，各自使用独立的新容器，请求均为冷缓存且 0 失败。单请求 prefill 使用随机 token，ISL 260016 和 1000016，`max_tokens=1`。

| `bounded-prefill` | C128 输出 token 吞吐 | C256 输出 token 吞吐 | C256 总 token 吞吐 | 260K 单请求 Prefill TPS | 1M 单请求 Prefill TPS |
|---|---:|---:|---:|---:|---:|
| 关闭 | 843 token/s | 1109 token/s | 9979 token/s | 9077 token/s | 4776 token/s |
| 开启 | 1286 token/s | 1369 token/s | 12317 token/s | 9067 token/s | 4772 token/s |
| 变化 | +52.6% | +23.4% | +23.4% | -0.1% | -0.1% |

`bounded-prefill` 的收益来自高并发下更少的静态预留；两档单请求 prefill 的吞吐差异约为 0.1%。

</details>
<details>
<summary>查看 OMP、EPLB 和 custom AG/RS 对照</summary>

1M 配置。固定 10-token prompt，先跑 C128 热身再测 C256，每个请求输出 128 token。基线是 OMP 8、EPLB、SM80 custom AG/RS 同时开启。

| 配置 | C128 输出 token 吞吐 | C256 输出 token 吞吐 | C256 总 token 吞吐 | C256 变化 |
|---|---:|---:|---:|---:|
| OMP 8 + EPLB + custom AG/RS（基线） | 3016 token/s | 4338 token/s | 4677 token/s | — |
| 关闭 EPLB | 2952 token/s | 4147 token/s | 4471 token/s | -4.4% |
| 关闭 custom AG/RS | 2335 token/s | 3815 token/s | 4113 token/s | -12.1% |
| OMP 1 | 2493 token/s | 2753 token/s | 2968 token/s | -36.5% |
| 同时开启 `decode-metadata` 与 `ragged-reuse` | 1908 token/s | 3969 token/s | 4279 token/s | -8.5% |

该负载下，EPLB、custom AG/RS 和 OMP 8 的组合吞吐较高，保留为默认配置。两个实验开关组合后 C256 下降，继续不纳入默认配置。

</details>
<details>
<summary>查看 prefill-throttle 的吞吐与延迟取舍</summary>

1M 配置。decode C64（ISL 1024）加 262K prefill 的闭环混合负载，只切换 `prefill-throttle`。300 秒测量窗口，两组失败率均为 0。两条流分别统计，分母是场景的完成墙钟。

| 配置 | Decode 流输出 token 吞吐 | Decode 流 TTFT P50 / P95 | Decode 流 TPOT P50 | Decode 流 ITL P95 | Prefill 流输入 token 吞吐 | 整机总 token 吞吐 |
|---|---:|---:|---:|---:|---:|---:|
| 关闭（基线） | 783.5 | 1.73 / 12.73 s | 73.7 ms | 2.09 s | 6546.6 | 8157 |
| 开启，每 4 个 step 释放一次 | 915.6 | 2.88 / 12.54 s | 61.0 ms | 1.88 s | 5384.8 | 7258 |
| 变化 | +16.9% | TTFT P50 变差 | -17.2% | -10.0% | -17.7% | -11.0% |

`prefill-throttle` 提高 decode 流的输出 token 吞吐并降低 TPOT，代价是 prefill 流的输入 token 吞吐下降、TTFT P50 增加，因此默认关闭，可按负载显式启用。

### 节流开启时的长请求容量

补充试验使用 1M 配置并开启 `prefill-throttle`，随机 ISL 1,047,000 / OSL 1,000 的请求同时进入。它与配置矩阵中关闭节流的容量测试采用不同调度条件。

| 并发 | 成功率 | 墙钟 | 输入 token 吞吐 | 输出 token 吞吐 | 总 token 吞吐 | TTFT P50 / P95 | TPOT P50 / P95 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 4 | 4/4 | 629.7 s | 6651 | 6.35 | 6657 | 264.5 / 625.8 s | 9 / 239 ms |
| 16 | 16/16 | 2878.2 s | 5820 | 5.56 | 5826 | 1308.9 / 2873.3 s | 296 / 382 ms |

当次每个引擎的 KV cache 可容纳 4,226,760 token，单 GPU 可用 KV 内存为 10.65 GiB。C16 超过即时容量后排队，全部请求完成、无错误或中止，结束后 KV 使用率回到零。对应单流输入吞吐观测为 4501 和 4757 token/s；批量试验存在 prefill/decode 重叠，不能仅按并发倍数外推。

C4 与 C16 使用相同 seed，C16 前四个 prompt 与 C4 相同。C16 第一个请求命中此前留下的前缀缓存，TTFT 为 2.8 s，其余为 235.1–2873.3 s，因此 C16 总耗时略偏乐观。该表保留这一缓存条件，不作为全冷 KV 成绩。

</details>

## 未采用方案

以下方案未进入默认配置：compact MQA 未满足输出一致性和成功率要求；两种 CPU KV offload connector 未通过初始化或请求验证；adaptive DSpark 缺少所需 backend 支持；TP8、logits 分块和 `dummy_q` 初始化方式未显示明确收益。
