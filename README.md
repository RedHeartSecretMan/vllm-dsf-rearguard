vllm-dsf-rearguard deploys DeepSeek-V4.1-Flash-1017 on `8×A100-SXM4-80GB / NVSwitch`. It adds an adaptation layer to a pinned vLLM image and ships tools for weight verification, image builds, service launch, functional acceptance and performance testing. The repository does not include model weights or prebuilt images.

DSF stands for DeepSeek-V4.1-Flash; Rearguard means a rear-guard unit.

## Why vllm-dsf-rearguard

- **SM80 support.** Upstream vLLM does not cover the A100 (SM80) path for DeepSeek-V4.1-Flash. This project adds what A100 needs for sparse MLA, the FP8 KV cache, DSpark speculative decoding and EP8 communication.
- **1M context that works.** Eight 80GB A100s launch with a 1M context and serve real 1,047,000-token inputs, with images, video and tool calls.
- **Video, too.** The DeepSeek-V4.1-Flash checkpoint has image delimiters but no trained video delimiters. The adaptation layer samples each video into up to 32 frames and wraps them in a stable text prompt, so the model reads a video as an ordered, timestamped sequence of image frames. Multi-turn requests can refer back to the same video.
- **Everything pinned.** The base image is pinned by digest, the model by revision and per-file SHA256, and the adaptation layer by file fingerprints. Any mismatch stops the launch.
- **Every recommended configuration fully tested.** Each one passed performance, functional, protocol and accuracy tests, and the data and test tools are published.

`launch.py` builds a launch plan first. When it starts the service, it verifies the weights, image sources and GPU state, then creates the container. Inside the container, the pinned vLLM and the adaptation layer run two DP replicas (TP4 each) with EP8 expert parallelism across all 8 GPUs. See [Architecture](docs/architecture.md) for details.

It is generated with [Archify](https://github.com/tt-a1i/archify) from [architecture.archify.json](docs/assets/architecture.archify.json).

## Supported scope

| Item | Scope |
|---|---|
| Model | DeepSeek-V4.1-Flash-1017 at a pinned [ModelScope](https://modelscope.cn) revision |
| Hardware | `8×A100-SXM4-80GB / NVSwitch` |
| Parallelism | `TP4 / DP2 / EP8` by default; `TP8 / EP8` also supported |
| Context | 262144, 524288 and 1048576 tokens (262K, 524K and 1M) |
| Inputs | Text, images and tool calls; video is sampled into image frames on the server |
| API | OpenAI-compatible Chat Completions and Responses |

## Quick start

### 1. Prepare the environment

You need Linux, Python 3.10 or later, [Docker](https://www.docker.com/), the [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/), a working CUDA driver and 8 idle A100-SXM4-80GB GPUs. Download `deepseek-ai/DeepSeek-V4.1-Flash-1017` from ModelScope in advance; the full directory is about 510 GB. The revision and file list are in `manifests/model-files.json`.

```bash
export MODEL=/path/to/DeepSeek-V4.1-Flash-1017
```

### 2. Verify the model

Full verification reads every weight file, computes SHA256 and writes the result to `runtime/model-verified.json`. The launcher reads this file.

```bash
python3 scripts/model_check.py "$MODEL" --full --output runtime/model-verified.json
```

### 3. Build the image

The build script uses committed sources only and produces the `vllm-dsf-rearguard:dev` image, then checks the adaptation layer in a container without GPUs. It refuses to build if the working tree has uncommitted changes.

```bash
bash scripts/build.sh
```

### 4. Generate a launch plan

Generate a launch plan to check the model path, port and launch arguments. This step only prints the plan; it does not create a container or use any GPU.

```bash
python3 launch.py "$MODEL" \
  --parallel tp4dp2 --dspark 5 --max-seqs 256 \
  --context 1048576 --chunk 16384 --memory 0.90 \
  --experimental stacked-kv --experimental bounded-prefill \
  --no-disable-chunked-mm-input --responses-store \
  --port 6789
```

### 5. Start the service

Once the plan looks right, add `--start`. Before starting, the launcher checks the image sources, the model verification result and that all 8 GPUs are idle; it stops if any check fails.

```bash
python3 launch.py "$MODEL" \
  --parallel tp4dp2 --dspark 5 --max-seqs 256 \
  --context 1048576 --chunk 16384 --memory 0.90 \
  --experimental stacked-kv --experimental bounded-prefill \
  --no-disable-chunked-mm-input --responses-store \
  --port 6789 --start
```

The service listens on `127.0.0.1:6789` only, under the `/v1` prefix, with the model name `deepseek-ai/DeepSeek-V4.1-Flash-1017`. Startup re-verifies all weights, and model loading and graph capture take a while. The default container name is `vllm-dsf-rearguard`; follow progress with `docker logs -f vllm-dsf-rearguard` and send requests after `/health` returns success.

### 6. Send a request

```bash
curl http://127.0.0.1:6789/health
curl http://127.0.0.1:6789/v1/models

curl http://127.0.0.1:6789/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "deepseek-ai/DeepSeek-V4.1-Flash-1017",
    "messages": [{"role": "user", "content": "Introduce yourself in one sentence."}],
    "max_tokens": 128
  }'
```

## Configuration guide

The quick-start configuration is a good first deployment: 1M context, 16K chunk, 0.90 memory utilization, with multimodal chunking, `stacked-kv` and `bounded-prefill` enabled.

| Flag | Recommendation |
|---|---|
| `--context` | Pick a context that fits the longest input plus the maximum output |
| `--memory` | Start at `0.90`; if you need more KV capacity, validate `0.925` or `0.95` on your workload |
| `--chunk` | Set `16384` explicitly; `32768` needs more memory headroom and requires `0.95` with a 1M context |
| `--no-disable-chunked-mm-input` | Enable for large images, many images or video |
| `--responses-store` | Enable if you need `previous_response_id`; in-memory history is LRU-bounded by `VLLM_RESPONSES_API_STORE_MAX_SIZE` (default `10000`) and stays in the current service process |
| `--experimental` | Repeatable. `stacked-kv` and `bounded-prefill` from the quick start are fully tested; validate other options on your workload |

The startup log reports the actual KV capacity. Throughput, latency and capacity trade-offs for different workloads are in [Performance](docs/performance.md).

## Local checks

These checks need no GPU and match CI. CPU PyTorch is used for hot-path checks and some unit tests; the few tests that need the image or the model tokenizer are skipped automatically.

```bash
python3 -m pip install ruff numpy torch --extra-index-url https://download.pytorch.org/whl/cpu
ruff check .
python3 -m unittest discover -s tests -v
CUDA_VISIBLE_DEVICES= python3 -m scripts.hotpaths.check
```

GPU acceptance needs the target hardware and a running service; see [test method](docs/performance.md#测试方法).
